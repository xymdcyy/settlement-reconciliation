# 关键决策记录

> 本文档记录系统架构中的所有关键决策及其理由。
> 当需要修改架构时，必须先阅读本文档，理解决策背景。

## 决策 1：以台账为中心，而非以匹配为中心

**背景**：
- 现有系统（v1.0）以"自动匹配"为核心，先上传再匹配
- 实际业务中，200 客户只有 50-80 个需要对账，其余直接按台账开票

**决策**：
以"台账"为数据中心，对账、开票、红冲都是台账上的操作（视图和动作）。

**理由**：
1. 台账是 200 客户的共性，匹配只是 50-80 客户的个性
2. 开票状态挂在台账行上，对账结果也回写到台账行——状态只有一份
3. 无对账单客户也能用系统（台账+开票），不需要单独搞一套简化系统

**影响**：
- 数据模型：receipts 表是核心，包含系统字段+开票状态+扩展字段+差异判断
- 前端：三张桌子（台账/核对/开票）共享同一批数据
- 现有代码：引擎保留，但降级为"核对桌"的内部模块

**替代方案**：
- 两层分立（第一层管台账，第二层管对账）——状态同步噩梦
- 以匹配为中心（现有架构）——覆盖不了 120-150 个无对账单客户

## 决策 2：核心集 + 可选扩展列

**背景**：
- 200 个客户的台账手工区列名各不相同（是否开票/发票号/开票日期/拆分/备注是共性，但潍坊百货有红通号，日照凌云有台数）
- 如果强制统一，潍坊百货会偷偷加列；如果完全灵活，三年后又是 200 套异构 schema

**决策**：
- 核心集 5 列（billing_status/invoice_no/invoice_date/split_note/remark）所有客户强制
- 扩展列客户级配置，需主管审批后生效
- 存储用 JSONB（extra_fields），配置存 customers.extra_fields_config

**理由**：
1. 核心集覆盖 80% 场景，强制统一
2. 扩展列覆盖 20% 特殊场景，灵活但可控
3. JSONB 避免动态加列导致的 schema 爆炸
4. 审批制防止随意扩展

**影响**：
- 数据模型：receipts.extra_fields JSONB
- 前端：扩展列动态渲染（根据 customers.extra_fields_config）
- 迁移：需要为每个客户编写迁移规则 YAML

**替代方案**：
- 完全统一（只留核心集）——潍坊百货等特殊场景无法支持
- 完全灵活（每客户一套列）——三年后又是 Excel 乱象

## 决策 3：父子行模型处理拆分

**背景**：
- 业务场景：一行签收记录 5 台，需开 3 台发票，剩 2 台下次开
- 现有做法：Excel 里插入行，改数量，标"已拆分"

**决策**：
- 父行不删除，标记 billing_status='split'
- 生成子行，split_parent_id 指向父行
- 子行继承父行全部系统字段，仅 quantity/amount 不同
- 子行可再拆分（递归），但不可跨父行合并
- 子行的 receipt_no 与父行相同（数据库允许多行同单号）

**理由**：
1. 保留完整审计痕迹（父行不删除）
2. 子行可独立开票、独立红冲
3. 递归拆分支持复杂场景（5台拆3+2，2再拆1+1）
4. 血缘清晰（通过 split_parent_id 追溯）

**影响**：
- 数据模型：receipts.split_parent_id 自引用
- 唯一性约束：receipt_no 不唯一
- 查询：需要递归查询（某父行的所有子行）

**替代方案**：
- 数量字段（receipts.quantity_billed）——无法支持部分开票、部分红冲
- 删除父行，只留子行——丢失审计痕迹

## 决策 4：试点 → 全量，分批切换

**背景**：
- 200 客户全量上线风险高（数据迁移错误、财务抵触、系统 bug）
- 但逐个客户滚动上线，并行期太长（200 客户 × 1 周 = 4 年）

**决策**：
- 试点 4 客户（潍坊百货/全福元/河北劲草/天猫优品），1-2 个月
- 全量推广分 2 批次：有对账单客户（50-80）→ 无对账单客户（120-150）
- 每批次内，每月迁移 10-30 个客户

**理由**：
1. 试点验证标准、工具、流程，降低全量风险
2. 分批切换，每批有冻结期，业务影响可控
3. 有对账单客户优先（复杂度高，先啃硬骨头）

**影响**：
- 项目周期：6-12 个月全量上线
- 需要培训计划、迁移计划、回滚机制

**替代方案**：
- 一刀切全量上线——风险太高
- 逐个客户滚动——周期太长

## 决策 5：冻结期 + 全量导入

**背景**：
- 业务不能停，但迁移期间不能更新 Excel（否则数据分叉）
- 历史数据必须全量导入（红冲要翻历史蓝票）

**决策**：
- 冻结期 1-2 周：业务继续，但不更新 Excel，新数据记录在临时表
- 冻结期内：全量导入历史数据 + 验证
- 解冻后：系统上线，补录冻结期数据

**理由**：
1. 全量导入保证数据完整性（红冲场景需要）
2. 冻结期避免数据分叉
3. 补录机制保证业务连续性

**影响**：
- 需要提前通知团队
- 需要临时表机制（纸质/临时Excel）
- 需要导入验证工具

**替代方案**：
- 增量迁移（只迁近N个月）——红冲查不到老蓝票
- 并行期（Excel和系统同时用）——数据分叉

## 决策 6：保留现有引擎架构

**背景**：
- 现有系统已有天猫/重百两个引擎（2700 行代码）
- 引擎采用插件化架构，接口清晰

**决策**：
- 保留 app/engines/ 整个目录，一行不改
- 引擎降级为"核对桌"的内部模块
- 新客户接入时，复用现有引擎架构

**理由**：
1. 引擎架构本身是对的（插件化、接口清晰）
2. 天猫引擎已验证（匹配率≥95%）
3. 重写成本高，收益低

**影响**：
- 现有代码：engines/ 不动，services/routers 重排
- 新客户接入：复用引擎模板

**替代方案**：
- 推倒重来——浪费现有投资
- 并行两套系统——架构失败

## 决策 7：财务-客户归属模型

**背景**：
- 每个客户有一个财务专员负责
- 一个财务专员负责多个客户
- 现有 Excel 分散在各人电脑

**决策**：
- user_customer_assignments 表维护归属关系
- 工作台首页显示"我负责的客户"
- 权限控制：财务只能看自己负责的客户

**理由**：
1. 符合实际工作分工
2. 权限清晰，避免越权操作
3. 工作台聚焦，减少干扰

**影响**：
- 数据模型：user_customer_assignments 表
- 前端：工作台首页按归属筛选
- 后端：API 权限检查

**替代方案**：
- 全部客户所有人可见——权限混乱
- 按角色分组（不按客户）——不符合实际分工

---

## 决策 8：SQLite（开发）+ PostgreSQL（生产）

**背景**：
- 现有系统用 SQLite（开发）
- 生产环境需要支持 JSONB、并发、性能

**决策**：
- 开发环境：SQLite（简单，无需安装）
- 生产环境：PostgreSQL（JSONB 支持，性能好）
- 通过环境变量 DATABASE_URL 切换

**理由**：
1. SQLite 开发方便，无需安装数据库
2. PostgreSQL 生产稳定，JSONB 支持灵活查询
3. SQLAlchemy 抽象层，切换成本低

**影响**：
- 数据模型：JSONB 字段在 SQLite 下存 TEXT（序列化）
- 迁移工具：需要考虑两种数据库的差异

**替代方案**：
- 全部用 SQLite——生产环境性能不足
- 全部用 PostgreSQL——开发环境配置复杂

---

## 决策 9：不放在试点的唐山百货特例

**背景**：
- 唐山百货台账结构特殊（手工区在别的 sheet，客户对账单混在台账里）
- 试点期应该验证共性，而非个性

**决策**：
- 唐山百货不放入试点
- 但标准台账设计时预留扩展能力（扩展列、自定义 sheet 解析）

**理由**：
1. 试点期应该验证共性（80%客户是标准结构）
2. 唐山百货的特例可以在全量推广时单独处理
3. 标准设计预留扩展能力，不会被特例卡死

**影响**：
- 试点客户：潍坊百货/全福元/河北劲草/天猫优品
- 全量推广：唐山百货单独处理

**替代方案**：
- 放入试点——增加试点复杂度，可能拖慢进度

## 决策 10：文档先行，充分评审后再开发

**背景**：
- 项目复杂（业务重塑+数据迁移+多人协作+200客户推广）
- 没有充分文档就动手，会把 Excel 乱象搬进数据库

**决策**：
- 先写 5 份核心文档（业务模型/数据模型/系统设计/迁移计划/决策记录）
- 团队评审通过后再开始开发
- 开发过程中，文档持续更新

**理由**：
1. 文档是团队的共同语言
2. 评审可以提前发现问题，降低返工成本
3. 文档是后续维护的基准

**影响**：
- 项目周期：增加 1-2 周文档时间
- 但降低了开发期的返工风险

**替代方案**：
- 边开发边写文档——容易走偏，返工成本高
