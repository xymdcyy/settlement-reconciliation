## 架构总览

### 核心思想

**以台账为中心，三张桌子（台账/核对/开票）共享同一批数据。**

- 200 客户共用：台账 + 开票
- 50-80 客户额外：核对（引擎插件化）
- 所有功能都是台账上的视图和动作

### 数据模型核心

```
receipts（台账行）⭐
  ├─ 系统字段（94列提取物）
  ├─ 开票状态（核心集：billing_status/invoice_no/invoice_date/split/remark）
  ├─ 扩展字段（JSONB，客户级配置）
  ├─ 差异判断（diff_type/diff_note/resolved_period）
  └─ 父子行（split_parent_id，支持拆分）

customer_statements（客户对账单）→ 核对桌专用
match_results（匹配结果）→ 核对桌专用
invoices（发票记录）
adjustments（调账/红冲记录）
```

### 功能模块

```
工作台（首页）
  └─ 我负责的客户列表 + 本月待办

客户详情页
  ├─ Tab 1: 台账桌（200客户）
  ├─ Tab 2: 核对桌（50-80客户）
  ├─ Tab 3: 开票桌（200客户）
  ├─ Tab 4: 未决池
  └─ Tab 5: 红冲工具

系统管理（主管）
  ├─ 客户管理
  ├─ 扩展列配置
  ├─ 引擎配置
  └─ 数据迁移
```

## 关键决策摘要

| 决策 | 理由 | 影响 |
|------|------|------|
| 以台账为中心 | 200客户共性，状态只有一份 | receipts 表是核心 |
| 核心集+扩展列 | 共性强制，个性灵活，审批可控 | JSONB + 配置驱动 |
| 父子行模型 | 保留审计，支持递归拆分 | split_parent_id 自引用 |
| 试点→全量 | 降低风险，验证标准 | 4客户试点，6-12月推广 |
| 冻结期+全量导入 | 数据完整性，避免分叉 | 需提前通知+临时表 |
| 保留现有引擎 | 架构正确，已验证 | engines/ 不动 |
| 财务-客户归属 | 符合实际分工 | user_customer_assignments |
| SQLite+PostgreSQL | 开发简单，生产稳定 | 环境变量切换 |
| 唐山百货特例不试点 | 验证共性，预留扩展 | 全量时单独处理 |
| 文档先行 | 避免走偏，降低返工 | 增加1-2周文档时间 |

详见 [05-decisions.md](05-decisions.md)

## 与现有系统的关系

### 保留

- `app/engines/` 整个目录（天猫/重百引擎、base接口、注册表）
- `customer_settlements` / `match_results` / `correction_logs` 表
- 匹配引擎的插件化架构

### 改造

- `our_receipts` → `receipts`（加开票状态、扩展字段、父子行）
- `upload_service` → 层累追加台账
- 前端：从"上传→匹配"流程改为"台账常驻，核对是台账上的动作"

### 新建

- 工作台（首页）
- 台账桌、开票桌、未决池、红冲工具
- 系统管理（客户/扩展列/引擎/用户）
- 迁移工具（Excel解析/清洗/验证）

### 废弃

- 现有前端的"上传页/工作台页"交互逻辑
